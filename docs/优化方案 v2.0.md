# Edge Rush 优化与上线方案 v2.0

> 日期：2026-10-28  
> 目标：先做出愿意反复玩的竖屏擦边游戏，再验证 TapTap 分发与激励广告收入。  
> 基线：优化方案 v1.0、README、现有 C# 源码及广告／上架文档。  
> 本轮交付：方案文档；没有修改代码，也没有执行 Unity 运行或 Android 真机验证。  
> 本文确定后，作为下一轮改代码与验收的工作基线；v1.0 保留供对照。

## 1. 结论与范围

保留“三车道、单指变道、擦边连击、霓虹公路”的核心。当前最需要的是操作可信、失败公平、目标清晰和广告闭环可靠，随后才是内容数量。

沿用 README 已写明的 **TapTap 国际版、Android、免费游玩、主动选择激励广告** 路线。首发语言以英文为主，代码抽出文案键，为后续中文留接口。若改为中国大陆 TapTap，需要另做发行资质、广告网络、隐私与平台服务评估，不能直接复用国际版结论。

| v1.0 提案 | v2.0 决策 | 原因 |
| --- | --- | --- |
| 用固定坐标移动、扩大面板修 UI | 改为安全区内的锚点、内容区和自适应布局 | 扩面板只能修特定比例，无法解决窄屏和长屏 |
| 立即扩至 10 款车，最高价 15000+ | 首版精修现有 7 款，新增 3 款留到后续 | 先验证解锁节奏与视觉价值 |
| 同时开发 5 个道具 | 首版磁铁＋护盾；双倍金币待数据验证；慢速、冲刺后置 | 降低计时、碰撞、可解性与得分平衡复杂度 |
| 高级车变道更快、碰撞箱更小 | 全车相同操控、碰撞与计分规则 | 让玩家相信成绩来自操作 |
| 引导只播放 3 秒 | 用实际操作完成教学，可跳过、可重播 | 看过提示不等于学会 |
| 先修 UI、皮肤、五道具 | 先修稳定性与 UI，再教学／核心体验，再小规模内容，最后商业化验证 | 减少返工，提前暴露盈利路线风险 |

以下数值均为**首轮调参起点或内部验收目标**，不是平台要求、行业基准或收益保证。

## 2. 现状核对与优先问题

目前已有可运行工程结构：核心跑局、擦边倍数、图案库、车库、签到任务、存档、程序化视听和广告抽象层。项目锁定的编辑器版本为 `6000.6.7f1`，后续先沿用此版本，避免顺便升级引入干扰。

### 2.1 已从代码确认的问题

1. **测试广告跳过后缺少回调。** `Ads.cs` 的 SKIP 调用 `Finish(false)`，但未传入 `Play` 收到的回调；`StopAllCoroutines()` 又停止了正常完成路径，导致 `AdManager._showing` 可能无法复位、音频压低状态无法恢复。列为 P0，必须覆盖完成、跳过、关闭、失败四条路径。
2. **发布包可能显示 Mock。** `CreateProvider()` 在未启用真实 SDK 等情况下回退到 Mock；`IsConfigured()` 只检查任意 ID 非空，当前官方测试 ID 也能通过。Release 必须做构建校验，缺配置时报错，运行时必要时禁用广告，不能静默回退测试视频。
3. **展示统计过早。** `AdImpression` 在调用 SDK 展示前记录，未必真的曝光。改为展示请求、打开、曝光、奖励、关闭、失败分开统计，曝光与收入以 SDK 对应回调为依据。
4. **初始化与加载没有可靠状态边界。** 管理器发起初始化后立即标记完成并加载；适配器内部也加载。需要消除重复加载、并发请求覆盖和旧回调写回问题，并补有上限的退避重试。
5. **可解性检测是近似模型。** `Patterns.cs` 依据行间隔和变道时间推算可达车道，没有完整模拟卡车长度、移动车轨迹、图案边界及实际碰撞时间。至少一条空车道不代表玩家来得及到达。
6. **现有慢动作会影响操作。** `RunSession.Tick` 把缩放后的 `dt` 传给玩家、障碍、道路和连击。若直接套用 v1.0 慢速道具，会同时拖慢变道手感；需要先明确时钟边界。
7. **统计尚未形成运营数据。** 本地日志可用于排错，但不足以直接分析跨日留存、分版本漏斗和真实收入。

### 2.2 需要 Unity 或真机确认的项目

- Garage、Quests、HUD 的真实裁切、按钮遮挡和输入区域冲突。
- 暂停、切后台、广告往返后的状态与音频恢复。
- 霓虹叠加是否遮住障碍，长局是否产生 GC 卡顿、过热或内存增长。
- 金币到账、广告奖励及旧存档升级是否可靠。

v1.0 的 UI 根因不能只凭坐标下结论：CanvasScaler、安全区、锚点和实际元素边界都参与结果。“按钮在 y=290 偏右”中的 y 很可能是 x 的笔误，修改前以代码和画面为准。

## 3. 核心体验：让玩家理解为什么赢、为什么输

### 3.1 产品表达与操作

一句话卖点：**“贴着车流变道，把擦边连成五倍。”** 菜单、教学、结算和商店视频都围绕这个动作表达。

- 保留点击左右半屏与左右滑动；一次手势最多产生一次变道请求，不能抬手时再重复触发。
- UI 消耗过的触摸不能传入玩法；多指、取消触摸、跨暂停的旧手势必须清理。
- 保留 0.12 秒变道作为基线，先验证响应，不因皮肤改变手感。
- 结算突出本局擦边数、最高倍数和距纪录差值，主按钮是“再来一局”；广告奖励为次级选择。

### 3.2 教学从“看提示”改为“做一次”

独立教学路段依次完成左变道、右变道、一次安全擦边；目标完成即推进，没有强制阅读长文本。失败后原地重试，允许跳过；设置里可重播。

- 教学不计正式纪录、任务、经济收益与广告资格。
- 存 `tutorialVersion` 与完成状态，后续更新不重复强制老玩家教学。
- 第一局用宽松交通和明确金币引导，不在首次接触时同时介绍全部系统。
- 新玩家前 3 个正式完成局不主动露出复活／结算广告入口；车库主动访问的外观广告可保留清晰说明。用统一资格策略实现，不能只限制复活。

### 3.3 难度与交通公平

先沿用原难度曲线收基线数据，避免同时重写所有数值。体验目标：前 15 秒学会操作，15–45 秒理解擦边，45 秒后逐步增加交通组合压力；新手局长中位数先以 45–90 秒作为调参观察区间，不强制让玩家在该时间死亡。

交通验证需要：

- 按障碍实际占用时间窗检查路径，包含车辆长度、动态横移和跨图案衔接。
- 预算加入玩家反应时间与连续换道时间；首轮反应余量取 0.35 秒，结合真机调整。
- 预警与碰撞轨迹一致；移动车变道不能突然封住玩家唯一出口。
- 金币、道具只放在可抵达路径上，不能把玩家引入必死位置。
- 对常规、复活后、道具结束后三种状态分别检查；固定随机种子能够复现失败。
- 除自动验证外，实际试玩确认“容易读懂”。有解但无法识别的路段同样需要修改。

## 4. UI 与视觉改进

### 4.1 统一布局规范

保留现有 `SafeAreaFitter`，先验证其行为，再改屏幕内部布局，避免重复套安全区。

- 继续以 1080×1920 作为设计参考，边距使用设计单位；顶栏锚定安全区顶部，底部按钮锚定安全区底部。
- 菜单、车库、任务页共享金币组件。HUD 可简化尺寸，并明确区分“钱包余额”与“本局金币”，不追求全部机械一致。
- 任务卡改成标题／进度／奖励按钮三块不交叠的区域，用 LayoutGroup 或集中布局计算；内容放不下时滚动，返回按钮独立固定。
- Garage 预览和购买区分开，标题、余额、说明不互相挤占；金币不足时显示差额与正常获取方式。
- 点击目标至少约 48dp，并通过真机验证；Unity 设计像素不能直接当 dp。
- HUD 避开前方交通视野；道具状态放固定侧区，最多显示两个图标，不遮挡分数与暂停。
- 低血量闪光、震屏、拖尾提供减弱选项；不能只靠颜色识别道具或障碍。

验收比例覆盖 16:9、18:9、19.5:9、20:9，以及带刘海和底部手势区的设备；每类保留菜单、任务、车库、HUD、复活、结算截图。

### 4.2 皮肤：轮廓先于粒子

首版精修现有 7 款。基础车强调清晰，普通车增加条纹和不同尾部造型，稀有车加入克制的尾迹，高档车增加低亮度灯带与地面光效。所有车保留相同可见主体尺度、碰撞与变道规则。

- 高档车不做明显透明度脉动，避免玩家丢失车身位置；彩虹与闪烁不能盖住暖色障碍。
- 菜单预览可展示更丰富效果，局内特效受独立预算限制。
- `SkinDef` 保留稳定 `id`，增加 `rarity`、`visualProfileId` 等配置。展示档次与特效配置分开，不用大量布尔字段堆出组合。
- 外观纹理缓存复用，拖尾对象池复用；低画质减粒子和透明叠加，不改变玩法规则。
- 之后再加入 Arctic、Crimson、Platinum；首次扩充前先确认玩家已有收藏需求。

## 5. 道具系统：首版只上磁铁和护盾

| 道具 | 初始参数 | 明确规则 |
| --- | --- | --- |
| 磁铁 | 5 秒，横向最多相邻一车道 | 还必须在纵向吸附距离内；金币平滑飞向车，不隔整张地图吸取；先确保碰撞仍独立生效 |
| 护盾 | 抵挡 1 次碰撞，最长保留 20 秒 | 不叠层；触发后给 0.8 秒碰撞保护并安全处理触发障碍；同一障碍不能逐帧连撞或重复擦边计分 |

生成初值：正式跑局进行 15 秒后启用，每次在 **18–28 秒有效玩法时间** 后尝试生成，磁铁／护盾权重为 60%／40%。这些是尝试间隔，不承诺每次出现；没有安全位置就跳过。本局已有护盾时不再生成护盾；同屏最多一个待拾取道具。

共存规则：磁铁是一个计时增益槽，护盾是一个独立防护槽，可以同时生效。同类磁铁刷新至 5 秒、不累加。护盾到期有提前提示；不会在结算、广告或后台继续扣时。

碰撞／拾取顺序必须固定：护盾检测 → 致命碰撞裁决 → 存活情况下的金币／道具拾取 → 擦边结算。同帧先撞上障碍，不能靠同帧捡到护盾“事后免死”。触发护盾、复活保护穿过的障碍不计擦边。

死亡时结束磁铁与护盾；广告复活采用现有复活保护并重新清出安全区域，不恢复死亡前道具。任一时刻的保护来源统一查询，避免多个计时器相互覆盖。

后续道具：

- 双倍金币可在经济稳定后加入，只翻倍道具期间拾取金币，不扩大擦边／距离分；明确与结算翻倍的叠加。
- 慢速需拆分玩家输入时钟与世界运动时钟后再做。
- 冲刺需要重新验证得分、生成距离、结束缓冲和安全出口，首发暂缓。

### 5.1 时钟和模块边界

- 输入／变道：有效玩法实时时间，暂停时冻结，世界减速时保持响应。
- 世界：道路、障碍、距离受统一速度倍率驱动；速度改变时生成间距同步计算。
- 道具／连击：有效玩法计时，暂停、倒数、广告、后台均冻结；擦边演出慢动作不延长道具收益。
- UI／广告等待：独立非缩放时钟，不能因为玩法暂停而卡住。
- 分别记录现实局长、有效玩法时长与世界模拟时间，避免分析局长时混用。

建议新增 `PowerUpDefinition`、`PowerUpController`、`PowerUpSpawner`，让 `RunSession` 协调、`ObstacleManager` 管交通对象、UI 仅展示状态。道具配置集中到配置资产或现有 Tuning 配置层，不把对象池、图标、生成、效果全部塞进一个脚本。

## 6. 金币经济与轻量留存

### 6.1 先测金币来源，再定高价皮肤

不直接把 Gold Apex 从 3000 涨到 8000，也不在首版建立 30000 档。先保持现有价格兼容，测每局拾取、签到、任务、广告额外奖励的各自贡献。

初期体验目标：首款可购车在正常游玩约 3–5 局可获得，中档车约 2–3 个活跃日获得，高档车约 7–14 个活跃日获得。按真实玩家数据反推价格，不能把看广告当必要条件。

计算方式：预计解锁活跃天数 ≈ 价格 ÷ 每活跃日自然净收入。自然收入包括正常跑局、免费签到与任务；广告收益单独列出。签到当前奖励较高，需验证是否让“只签到不跑局”成为最优策略。

- 定义 `runCoins` 为本局实际拾取收入，`baseSettlement` 为可翻倍的结算基数；签到、任务不计入翻倍基数。
- 结算广告只补一次 `baseSettlement`，总到账为两倍；道具双倍若后续上线，在形成该基数之前计算一次。
- 所有到账记录来源、金额、余额与幂等键，结算／广告／任务各自只提交一次。
- 老玩家拥有的皮肤和广告进度保留，新增字段提供默认值。改价不撤销拥有权。

### 6.2 留存先做已有系统

- 每日任务固定一项容易完成、一项擦边练习、一项进阶目标；不能出现必须看广告才能完成的任务。
- 签到断签不清空已赚金币；建议保留七日进度，领完第七天后次日从第一天开启新轮，减少惩罚感。当前 `Clamp(..., 1, 7)` 会在连续签到时长期停留第七天，需要明确修正。
- 每天给一个清晰的下次目标：离下一辆车差多少，或下一项挑战是什么。
- 每周模式、成就、在线排行榜延后。先把已有任务做清楚，避免首版页面和长期维护成本膨胀。

## 7. 广告商业化路线

### 7.1 必须修正的前提：TapTap 上架不等于 AdMob 可完整变现

Google 当前支持关联的 Android 商店包括 Google Play 及其列出的第三方商店，**支持列表没有 TapTap**。仅发布在不支持商店的应用无法进行相应审核并会受限投放。因此，不能把“TapTap-only＋AdMob”当已经成立的完整收入路线。[来源：Google 商店关联说明](https://support.google.com/admob/answer/10037806?hl=en)

建议决策顺序：

1. 先完成 TapTap 国际版测试与获客，同时确认广告账户、主体、收款地区和包名。
2. 若采用 AdMob，规划同时发布到其支持且可实际使用的商店，并完成关联、账户与应用审核；准备广告平台要求的应用验证资料。
3. 若坚持仅 TapTap 分发，先向候选广告网络确认该分发方式、国家、主体资格与收款条件，再选 Provider；LevelPlay 等聚合也需要逐个确认需求方，不能默认保证填充。
4. SDK 选型可与玩法开发并行，但商业测试开始前必须解决。当前没有查看用户广告后台，也没有验证真实填充或到账。

AdMob 应用完整投放需经过 readiness 流程，测试广告成功不代表正式广告已获批准。[来源：Google readiness 说明](https://support.google.com/admob/answer/10564477?hl=en)

### 7.2 首版广告位与频控

优先把复活与结算翻倍做稳定；已有每日奖励和皮肤进度入口保留但可配置关闭，不额外扩充广告位。

| 广告位 | 用户价值 | 初始规则 |
| --- | --- | --- |
| 复活 | 保留本局继续挑战 | 每局 1 次；保留明确拒绝选项；展示前说明保护与恢复规则 |
| 结算翻倍 | 加快外观解锁 | 每局 1 次；明确显示将增加多少；基础金币先到账 |
| 每日额外金币 | 主动补充金币 | 保留每天最多 3 次，先检查奖励是否值得观看；不自动弹窗 |
| Chrome Ghost | 收藏外观 | 保留现有累计 5 次进度，显示 0/5；不诱导连续观看，无广告时不丢进度 |

首轮频控：全广告位共享 60 秒展示间隔；复活优先，复活后的短局结算可能因此没有广告入口。不叠加自动弹窗，不在跑局中主动弹广告。频控与资格在管理层统一执行，而非各页面自行判断。

广告不可用时显示稳定的禁用状态与简短原因，不在页面里突然挪动主按钮；保留完整免费玩法。进入展示前刷新可用性，防止“刚才 ready”到展示时失效。

### 7.3 奖励可靠性和生命周期

- 流程明确为：资格检查 → 请求展示 → 已打开／曝光 → 收到奖励资格 → 关闭返回。展示失败、用户关闭、未填充、初始化失败分别记录。
- 以 SDK 的奖励回调作为获奖依据；先用幂等键提交并持久化奖励，关闭回调只负责 UI／玩法恢复。不得仅凭关闭判断看完，也不得因为稍后的关闭异常撤回已获资格奖励。
- `showId` 对应一次展示，`runId + placement` 对应一局的一次性奖励；每日限额、皮肤进度同样防重入。
- 回调切 Unity 主线程再操作对象；重复、乱序、页面已销毁及过期回调均安全处理。
- 统一管理广告加载、展示、后台恢复和音频恢复；缺失回调有恢复路径，不能在广告仍在前台时简单超时继续跑局。
- SDK 对象关闭后销毁，单广告位单飞加载，失败指数退避，避免当前双路径重复全量加载。
- Mock 仅 Editor／Development 使用。增加可控制的成功、跳过、失败、延迟场景，正式构建禁止 Mock 与测试 ID。

Google 官方激励广告流程提供奖励、全屏事件及对象销毁接口，接入时应按最终锁定 SDK 版本核对，旧文档中的 v9.x 不能当固定最新版本。[来源：Unity 激励广告文档](https://developers.google.com/admob/unity/rewarded)

### 7.4 隐私与数据最小化

按发行地区与受众配置隐私流程；不能沿用“东南亚就可以先不做”的笼统结论。选择 AdMob 时，每次启动更新 UMP 状态，依据 `CanRequestAds()` 决定请求资格，提供所需隐私选项入口并防重复初始化／请求；拒绝个性化不应被直接当作所有广告都不可请求。[来源：Google UMP 指南](https://developers.google.com/admob/unity/privacy?hl=en)

公开隐私政策准确列明最终 SDK、数据用途、联系方式与用户选择；年龄／儿童定向配置依据实际产品受众和平台规则确定，不能由“有广告”直接推定为某个年龄分级。尽量不加与首版价值无关的 SDK 和权限。

### 7.5 收入用情景计算，不作承诺

广告日收入 ≈ DAU × 每 DAU 实际广告曝光 × 实际 eCPM ÷ 1000。

例如假设 1000 DAU、每人每日实际曝光 2 次、eCPM 为 5 美元，则为 10 美元／天。这只是算术情景；不能把旧文档的地区 eCPM 区间当预测。广告位数量也不等于实际曝光次数。

待实测后计算广告 LTV 与获客成本，计入素材、平台服务、税费和维护成本；没有留存／收入证据前不建议扩大付费推广。

## 8. 数据验证：先知道玩家卡在哪里

接入可导出、符合隐私要求的轻量分析服务；保留本地日志供排错。正式数据按版本、设备档位、国家、渠道、是否新用户分组，排除开发设备与测试流量。

必要事件：首次启动、教程步骤／完成／跳过、开局、死亡／主动退出／结算、擦边与最高倍数汇总、金币来源／消耗、皮肤预览／购买、广告入口可见／点击／请求／打开／曝光／奖励／关闭／失败、SDK 收入回调（如支持）。

必须携带匿名安装标识、会话标识、事件标识、版本、UTC 时间；跑局事件带 `runId`，广告带 `showId`。不记录广告 ID、原始 IP 等不必要个人数据。没有上传收入能力时，用广告后台按日对账，不根据奖励次数伪造收入。

| 指标 | 口径与首轮用途 |
| --- | --- |
| 教学完成率 | 完成人数／开始教学人数；内部观察目标 ≥85% |
| 首次会话再次开局率 | 完成首个正式局后再次开局的新安装数／完成首局的新安装数；观察目标 ≥60% |
| D1／D7 | 首次启动后第 1／7 个 UTC 日再次活跃的安装数／该首次启动 cohort；观察目标 D1 ≥25%、D7 ≥8% |
| 局长／死因 | P25／中位数／P75，按局数与是否复活拆分；定位开局劝退和无解路段 |
| 广告漏斗 | 可见→点击→展示请求→真实曝光→奖励；不同分母分别命名，避免把没填充误算为拒看 |
| 稳定性 | crash-free session 首轮目标 ≥99.5%；同时关注 ANR、卡顿、存档损坏 |
| 经济 | 每活跃日自然金币／广告金币、首次购买所需局数、皮肤选择分布 |
| 商业结果 | 实际收入／DAU、各国家 eCPM、实际曝光／DAU、填充、广告后流失 |

先找 10–20 位不熟悉游戏的人做可观察试玩，再争取 200–500 个有效新安装做方向性测试。留存必须等对应 cohort 成熟再算，并记录样本量和置信范围；小样本低于目标先排问题，不能直接宣布产品失败。首轮逐项调教学、交通与奖励，不同时改三类规则。

### 9.1 工程约束

- 继续沿用程序生成场景／美术的工程方式，本次不为改 UI 顺便改整个渲染管线或引入大型框架。
- 数值与玩法版本集中管理，支持回退；同一测试批次固定参数。
- 存档版本升级有迁移，皮肤 ID 不重命名；XOR／校验只作本地完整性辅助，不视为安全反作弊。
- 对随机交通可解性、奖励幂等、七日签到循环、存档迁移写有价值的自动检查；布局与手感以画面和实际操作验收。

### 9.2 验证层级

1. **编译**：运行现有离线检查，再由指定 Unity 版本编译运行；离线通过不代表 SDK 或 Android 可用。
2. **Editor Play Mode**：跑通菜单→教学→开局→暂停→失败→复活→结算→任务→车库；覆盖各分辨率，保存实际游戏截图。
3. **Android 真机**：至少一台低档和一台中档机，验证触摸、刘海、系统返回、切后台、断网、广告往返；没有设备就明确标记未验收，不能用 Editor 代替。
4. **Release 候选包**：IL2CPP／ARM64、正式包名与签名、版本号递增；从干净安装及旧版本升级两条路径验收。用测试设备配置验证 SDK，不自行点击正式广告。

性能内部预算：中档机目标 60fps（帧时间 P95 ≤16.7ms），低档机低画质稳定 30fps（P95 ≤33.3ms）；正式接 SDK 后测冷启动至可交互目标 ≤5 秒。稳定跑局不出现持续逐帧 GC 分配；连续玩 20 分钟并多次返回车库／广告后，内存无持续增长且无明显过热降频。未达标时先减透明叠加、纹理生成尖峰和重复分配，不能只限制粒子数量。

专项场景：磁铁到期／护盾触发／保护结束、同帧死亡与拾取、暂停时拾取状态冻结、广告跳过／失败／重复回调／返回后台、重复点击领取、领取后立即退出、连续签到第 7→8 天、坏档回退、旧档迁移。

## 10. 上线资料与旧文档纠正

- TapTap 国际版使用其国际开发者中心，按当前游戏创建与审核流程准备 APK 和资料；开发者注册条件与服务权限以官方及用户后台为准。[游戏创建](https://developer.taptap.io/docs/store/store-creategame/)／[开发者注册](https://developer.taptap.io/docs/store/)
- TapTap 开发者财务权限与第三方广告平台结算是两条链路，不能沿用旧文档“想赚广告钱必须通过 TapTap Verified”的推断。分别确认平台资格与广告收款资格。
- 图标、封面、截图、视频规格提交前按国际版后台复核，不将旧文档的尺寸、审核时长、包体积目标当固定平台规则。
- Android target API 按实际发行商店与锁定 SDK 的要求确定；旧文档关于未来 Google Play 日期／API 的断言本轮没有核实，不作为实施依据。
- 年龄分级依据实际问卷与广告配置；不能简单写“含广告通常就是 12+”。
- 需要可访问的隐私政策、支持联系渠道、SDK 清单、签名与密钥备份、稳定包名、版本号与 release 检查。
- 商店截图与视频必须来自实际 Unity／真机运行。现有 `art-preview-*.png` 是离线美术示意，不能充当已经实现的游戏截图。
- 若改走中国大陆发行，另开方案核验资质和可用商业路径；国内官方上架规则不能套用国际版。[国内规则参考](https://developer.taptap.cn/docs/store/standardies-operation/)
